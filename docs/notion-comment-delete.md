# 댓글 삭제 — 노션 측정 (2026-09-10)

comcom: "댓글 삭제 UI 및 기능이 없어. 노션에서는 어떻게 삭제를 지원하는지 찾아보고 구현해줘.
현정 테스트 팀스페이스에서 진행하고, 댓글을 직접 달아서 확인해줘. 그리고 Projects 표에서 댓글
아이콘을 눌러 열리는 곳에도 삭제 UI가 있는지 확인해줘."

원본에서 실제로 댓글을 달고, 메뉴를 열고, 지워 보며 잰 것이다. 잰 곳은 두 군데 —
**ComCom › Projects** 표의 행 댓글 팝오버(읽기 전용, 남의 댓글)와 **현정 테스트 › 새 페이지**
(내가 직접 단 댓글). 측정 스크립트와 원자료는 세션 scratchpad(`c*.mjs`, `n-*.jsonl`).

## 1. 어디서 댓글을 달고, 어디서 지우나

- **페이지 댓글의 진입점**: 제목 위에 마우스를 올리면 나오는 `아이콘 추가 · 커버 추가 · **댓글 추가**`.
  댓글이 하나라도 생기면 상단 바에 댓글 버튼이 함께 생긴다(없을 땐 없다).
- **표의 행 댓글 팝오버**(제목 셀의 댓글 배지 → 480 카드): 같은 댓글 행이 그대로 들어가고,
  **삭제 UI도 똑같이 있다.** 즉 comcom이 물은 "거기에도 삭제할 수 있는 UI가 있는지" 의 답은 **있다** 이고,
  페이지 안 댓글 섹션과 완전히 같은 어포던스다.

## 2. 댓글 위에 뜨는 툴바 — `댓글 작업`

마우스를 올리면 그 댓글의 오른쪽에 `aria-label="댓글 작업"` 툴바가 뜬다(평소 opacity 0).

| 대상 | 크기 | 버튼 (각 24×24) |
|---|---|---|
| 스레드 머리 | 76×28 | `리액션 추가` · `해결` · `추가 작업` |
| 그 외 댓글(답글) | 52×28 | `리액션 추가` · `추가 작업` |

- 팝오버에서 툴바의 오른쪽 끝은 카드 오른쪽 끝에서 **16px 안쪽**(카드 right 1141, 툴바 right 1125).
- `해결`은 **남의 댓글에도** 있다 — 해결은 작성자 전용이 아니다.

## 3. `추가 작업`(⋯) 메뉴 — 여기에 삭제가 있다

폭 **180**, radius **10px**, 행 높이 **28**, 글자색 **rgb(44,44,43)**, 행 간격 29, 그룹 사이 구분선(+8).

| 누구의 댓글인가 | 항목 |
|---|---|
| **남의 댓글** (2줄) | 읽지 않음으로 표시 · 링크 복사 |
| **내 댓글** (5줄, 높이 160) | 읽지 않음으로 표시 · **편집하기** · 링크 복사 ―구분선― 답글 알림 끄기 · **삭제하기** |

- 즉 **편집과 삭제는 작성자만**. 워크스페이스 멤버라고 남의 댓글을 지울 수 없다.
- **삭제 항목은 빨갛지 않다** — 다른 항목과 같은 잉크다(우리 repo의 `danger` 빨강 관례와 다르다).
- 수정된 댓글은 날짜 옆에 `(편집됨)` 이 붙는다.

## 4. 삭제 확인창

`삭제하기` 를 누르면 모달이 뜬다. 바로 지우지 않는다.

| 항목 | 값 |
|---|---|
| 카드 | 324 × 145, radius **12px** |
| 문구 | **이 댓글을 삭제하시겠습니까?** |
| 기본 버튼 | **삭제** — 글자 rgb(253,246,246) / 배경 **rgb(229,100,88)** (빨강 채움) |
| 그 아래 | **취소** — 배경 없음, 글자 rgb(44,44,43) |

두 버튼은 가로가 아니라 **세로로** 쌓인다(삭제가 위, 취소가 아래).

## 5. 스레드 머리를 지우면 답글은?

**남는다.** 루트 + 답글을 직접 만들고 루트를 지워 확인: 루트만 사라지고 답글은 그대로 남아
다음 댓글이 스레드 머리가 됐다(툴바 수 2 → 1). **캐스케이드 삭제가 아니다.**

이게 중요한 이유: 우리 서버도 한 행만 지우는데, 우리 패널은 `parentId === null` 인 것만 루트로
그려서 머리가 사라지면 답글이 **화면에서 사라지면서 배지 숫자에는 남는** 상태가 됐다. 원본과 같게
하려면 서버는 그대로 두고 **부모가 사라진 답글을 루트로 그리면** 된다.

## 6. 우리 앱에 반영한 것 (2026-09-10)

| 측정 | 반영 |
|---|---|
| 편집·삭제는 작성자만 | `api/comments/[commentId]` 에 `loadOwnComment` 추가. DELETE 와 PATCH{body} 는 작성자만(아니면 403), PATCH{resolved} 는 기존대로 멤버 누구나. 이전에는 **워크스페이스 멤버 누구나 남의 댓글을 지우고 고칠 수 있었다** |
| ⋯ → 삭제하기 | `CommentActions` — 페이지 댓글 섹션·표 행 팝오버(둘 다 `CommentRow`)와 사이드 패널(`CommentBubble`)에 모두 |
| 메뉴 180/28/10, 빨강 아님 | 그대로 |
| 확인창 324/12, 빨강 삭제 + 취소 | 그대로(문구도 동일) |
| 머리를 지워도 답글 유지 | 서버는 한 행만 삭제, 패널은 부모가 없는 답글을 루트로 렌더 |
| 남의 댓글엔 삭제 없음 | `me.id !== comment.authorId` 이면 툴바 자체를 안 그린다 — 공개 `/share` 에는 로그인 사용자가 없으므로 자동으로 안 뜬다 |

**구현하지 않은 것(측정은 됨)**: 리액션 추가 · 편집하기 · 링크 복사 · 읽지 않음으로 표시 ·
답글 알림 끄기, 그리고 툴바의 `해결`(패널에는 이미 따로 있다).

기하 제약: 댓글 행은 골든 검사 세 개가 픽셀로 잰다(아바타 = 첫 자식, 이름·날짜 = 첫 두 `span`,
본문 = 첫 `<p>`, 한 칸 64, 텍스트 열 32/46). 그래서 액션은 **행의 마지막 자식으로 절대배치하고
`span` 과 테두리를 쓰지 않는다**. 검사 `e2e/comment-delete.check.mjs` 가 이 조건까지 함께 지킨다.

## 7. 측정하면서 알게 된 것 (다음 사람용)

- 노션 컴포저는 **신뢰된 입력만** 받는다. `Input.insertText` 나 `document.execCommand('insertText')`
  로 글자를 넣으면 DOM 에는 보이지만 `댓글 보내기` 는 `aria-disabled="true"` 로 남는다. 실제
  `Input.dispatchKeyEvent({type:'char'})` 만 통한다 → **창이 가려져 있으면 아예 측정할 수 없다.**
- 창이 가려지면(`visibilityState: hidden`) 입력 1건에 5초가 걸린다. `Target.createTarget({newWindow:true})`
  로 내 창을 열고, 가려질 때마다 `Browser.setWindowBounds` + `Page.bringToFront` 로 앞으로 끌어와야 한다
  (scratchpad `cdp3.mjs` 의 `ensureVisible`). 다른 세션이 동시에 노션을 재고 있으면 서로 창을 뺏는다.
- 반대로 **메뉴를 열고 항목을 읽는 것**은 합성 클릭(`el.click()`)으로 충분해 가려져도 된다.
- 좌표를 캐서 실제 클릭하는 방식은 위험하다 — 이번에 `댓글 추가` 옆을 눌러 샌드박스 페이지에
  빈 하위 페이지 4개를 만들었다가 여백 마퀴 선택 + Backspace 로 지웠다. 삭제가 서버에 반영되기
  전에 탭을 닫으면 되살아나므로 **파괴적 조작 뒤에는 8초쯤 기다린 뒤 창을 닫을 것.**
