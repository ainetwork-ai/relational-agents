Inside the Family Passbook

An agent owns a wallet. Today it can spend that wallet on anything. This makes it a shared savings account: a family member signs what the agent may buy, the agent buys through Uniswap v3 once a week inside that permission and only inside it, and every purchase and every refusal is written where the family reads.

Three nouns carry the whole design — the mandate the family signs, the run that decides, the passbook that records. This page takes them in that order.

00 — orientation

What the chain enforces, and what only this code does

The single most useful thing to hold in your head: the mandate and its caps live entirely off-chain. Base has never heard of a mandate. It will move tokens for anyone holding the agent's key who asks properly — “once a week” and “twenty dollars a run” are promises this process keeps, not promises the chain keeps. The only bound the chain itself enforces is amountOutMinimum, the floor under what comes back from the swap.

Off-chain this process, on one machine. Nothing here is visible to anyone else, and nothing here is enforced by anyone else.

The colours split the same picture a second way — by who decided it, which is worth keeping separate from where it runs.

StandardWritten by someone else and not ours to change: EIP-712, ERC-20, the Uniswap v3 contracts, the ISO week. If we had spelled any of these differently, nothing would interoperate.
Our designProduct decisions another team would reasonably make differently: which eleven fields a mandate carries, that the passbook is a JSON file, that the cadence is weekly.
This project's rulesPolicy inside our code, each one pinned by a test: the refusal order, an unknown kind throwing, re-verifying the signature every run, a broadcast swap taking its period with it.

This is also the honest limit, stated plainly: a compromised agent process is unbounded, because every rule above sits inside it. Moving the caps onto the chain means a session key on a smart account or a v4 hook — a different project, named in plan.md as rejected scope rather than implied here.

01 — what the family signs

A permission with an address on it

The mandate is an EIP-712 typed message. A member signs it in their own wallet; the agent holds its own key and never a member's, so it cannot write itself one. Eleven fields go into the signature. Two deliberately stay outside it.

fieldtypewhat it decides
idstringnames this permission; the passbook files every line under it
roomIdstringwhich family this belongs to
agentaddressthe one wallet allowed to act on it
kindstringstanding repeats every period; oneoff happens once
tokenIn / tokenOutaddressthe only pair — USDC in, WETH out
perRunCapuint256the most one run may spend
perPeriodCapuint256the most a whole period may spend
periodstringthe cadence — week, day or month
expiresAtuint256after this second, every run is refused
nonceuint256orders replacements; the newest live one wins
approval—not signed. It holds the signature itself, so it cannot be inside it
revokedAt—not signed. Revoking must work after the fact, without the signer

Because the eleven signed fields exclude approval and revokedAt, a stored mandate re-verifies for as long as its terms are untouched — and stops verifying the moment one is edited. The agent re-recovers the signature on every run, so raising a cap by hand in the JSON file produces a refusal (approval-invalid), not a larger purchase.

The domain binds the chain: { name: "ainmem Family Passbook", version: "1", chainId }. A chainId passed as a string would be dropped by the signer and the same digest would verify everywhere, so mandateDomain throws on anything but a number or bigint.

    03 — idempotency
    
    One key decides whether this run already happened
    
  
    
  
    
    
    A scheduler can wake the agent as often as it likes; what stops a second purchase is the period
    key. It comes from the mandate's cadence, never from the calendar day — a weekly mandate keyed on
    days would buy seven times a week, which is the bug Uniswap's own DCA-bot guidance warns about.

    The week key is the ISO week, and the Thursday of that week fixes its year — which is why
    Friday 1 January 2027 keys as 2026-W53, not 2027-W01. Press the last two buttons:
    the calendar year turns over and the period does not.
    
    
    An invalid Date throws rather than keying as NaN-WNaN, which would
    silently merge every run of that mandate into one period.
    
  
    

    


    
  
    
    04 — one invocation
    
    The run, and what each exit writes
    
  
    
  
    
    
    runOnce never loops and never schedules itself — cron or the app's timer calls it.
    Every outcome it decides is written down; a refusal is a line the family reads, not a silent no-op.
    Passing dryRun keeps the whole decision and the real quote, and writes nothing.
    
  
    
  
      
    
    1. Read the passbook
      Mandates, what each period already spent, which periods are already bought. The ledger is the only state; there is no database in this layer.
      2. 
    
    2. Choose the mandate
      This agent's live standing mandate with the highest nonce. When none is live it takes the newest dead one on purpose.
      
      no mandate at all → outcome no-mandate, exit code 3
      
      Choosing the newest dead one is what makes the refusal say revoked or expired instead of “no mandate” — the difference between a family reading why, and a family reading a lost passbook.
      3. 
    
    3. Re-verify the signature
      Recover the signer from the stored approval and compare it to the subject. The passbook is a plain JSON file written by the agent's own process, so “the family allowed this” is only as true as the last time someone checked.
      
      does not recover → skip approval-invalid
      4. 
    
    4. Run the seven checks
      The gate above, with the intent built from the mandate itself: amountIn = perRunCap.
      
      any check fires → skip, with that reason
      5. 
    
    5. Quote
      QuoterV2, as a call that changes nothing. A quote of zero is a refusal of its own.
      
      nothing quoted → skip no-liquidity
      dry run stops here and returns the quote
      6. 
    
    6. Swap
      Approve exactly this amount, then exactInputSingle. The fill is read back from the transaction's own logs.
      
      threw before broadcast → skip swap-failed, the period stays open
      threw after broadcast → skip carries the tx hash, and that period counts as bought
      7. 
    
    7. Record the buy
      Amount in, amount out, price, transaction, the mandate that allowed it, and whether the decision was autonomous.
      
      passbook entry kind: "buy", keyed to this period
      8. 
  
    
  
    
    
    Why a failure after broadcast takes the period with it: the tokens may already have
    left. Treating it as “nothing happened” lets the next run buy on top of a purchase that did land. The cost of
    the other choice is one skipped week; the cost of this one is a double purchase, so the week loses. A
    confirmed revert is the one exception — the chain rolled every change back, so it carries no hash and the
    period stays open.
    
  
    

    


    
  
    
    05 — the Uniswap part
    
    Three calls, and two choices that are not obvious
    
  
    
  
    
    
    
      
    stepcallwhy this one
    
      
        
    quoteQuoterV2.quoteExactInputSinglereturns its answer by reverting, so it is a simulated call — a plain read cannot invoke it
    
        
    allowERC-20 approveexactly this buy's amount, never unlimited
    
        
    swapSwapRouter02.exactInputSinglewith amountOutMinimum from the executor's slippage bound
    
          
    
    
  
    
  
    
    
    The fill is read from the swap's own Transfer logs, not from a balance before and after.
    A balance difference also counts anything else that credited the same wallet in that window — two agents
    sharing a recipient would each write the other's purchase into the family's passbook. The logs of one
    transaction can only describe that transaction.
    
    
    Slippage is the executor's policy, not a signed term. The family signs caps on what goes
    in; perRunCap and perPeriodCap both bound tokenIn. A bound on what
    comes out needs a minimum-output field in the mandate, and that is honest work for a later slice
    rather than something to imply now.
    
  
    

    


    
  
    
    06 — findings
    
    Two things only the real chain told us
    
  
    
  
    
    
    Both were invisible on a local fork, and both are in FEEDBACK.md for the Uniswap team.
    A fork is one node; a public endpoint is a pool of them, and that difference is the whole story.
    
  
    
  
    
    
    
      
    The swap was estimated against an approval that had already landed
    
      
    On Base mainnet the approval was mined — receipt success, the allowance readable a moment
      later on every endpoint — but the node that estimated the swap was one block behind, so the router
      simulated against a zero allowance and reverted with STF.
    
      
    Fixed by waiting, bounded, until this client can read the allowance itself, before
      sending the swap. A single-node fork never shows it.
    
    
    
    
    
      
    An endpoint that answers quotes but refuses receipts
    
      
    One public RPC served quotes and balances and then refused
      eth_getTransactionReceipt for a transaction it had just mined. For a recurring-buy agent that
      is the worst failure available: the purchase landed and the agent cannot know it.
    
      
    Such a run is filed as “may have moved” and locks its period. The README now states the
      requirement — the endpoint must serve receipts.

    07 — your turn
    
    Run it yourself
    
  
    
  
    
    
    Everything above runs from one folder with no database and no app. The fork needs no key and no money.
    
  
    
  
    # a Base mainnet fork, in its own shell — no key, no funds
pnpm fork

# the agent and the grandmother are two of anvil's own test accounts
pnpm fund
pnpm mandate sign 20 100 90     # 20 USDC a run, 100 a week, 90 days
pnpm tsumitate                  # "bought", with the transaction
pnpm tsumitate                  # "skipped", "period-already-bought"
NOW=2026-10-05T09:00:00Z pnpm tsumitate   # a later week → "bought"

pnpm test                       # 69 tests; read the "skipped 0" line
pnpm web                        # the control panel, on 127.0.0.1:3120
